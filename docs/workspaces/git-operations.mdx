工作空间提供集成的 Git 操作来管理你的代码变更。

## 工作空间的 Git 基础知识

如果你不熟悉 Git，这里是你需要了解的内容：

<AccordionGroup>
<Accordion title="什么是分支？">
**分支**是一条独立的开发线。可以把它想象成你代码的副本，你可以在其中进行更改而不影响原始代码。

在工作空间中：
- **目标分支**（例如 `main`）- 你最终要合并回的"原始"分支
- **工作分支**（例如 `vk/abc123-task`）- 你进行变更的副本
</Accordion>

<Accordion title="什么是提交？">
**提交**是你变更的保存快照。就像游戏中的存档点 - 你随时可以回到它。

在工作空间中，提交会在 Agent 工作时自动发生，你也可以通过终端手动提交。
</Accordion>

<Accordion title="什么是 Pull Request (PR)？">
**Pull Request** 是将你的变更从工作分支合并到目标分支的请求。它会：
- 在一个地方展示你的所有变更
- 让团队成员审查你的代码
- 运行自动化测试（CI）
- 提供变更内容和原因的历史记录
</Accordion>

<Accordion title="什么是变基？">
**变基**用目标分支的最新变更来更新你的工作分支。就像在说"假设我从 main 的当前状态开始工作，而不是从旧状态开始。"

**何时变基：**
- 创建 PR 之前（避免冲突）
- 当目标分支有新提交时
- 当 Vibe Kanban 提示你时
</Accordion>

<Accordion title="什么是合并？">
**合并**将你的变更与目标分支组合。在工作空间中，这通常在代码审查后通过 GitHub 上的 PR 进行。

工作空间中的"合并"操作将目标分支拉取到你的工作分支中（与 PR 合并的方向相反）。
</Accordion>
</AccordionGroup>

## 仓库状态

右侧边栏中的 Git 部分显示：

| 信息 | 描述 |
|------|------|
| **仓库名称** | 当前仓库及其状态 |
| **当前分支** | 你的工作分支 |
| **目标分支** | 你要合并到的分支 |
| **未提交的变更** | 修改文件的数量 |
| **领先/落后** | 相对于目标分支的提交数 |
| **冲突指示器** | 存在合并冲突时显示 |

## 创建 Pull Request

<Frame>
<img style={{maxHeight: "400px"}} src="/images/workspaces-create-pr.png" alt="创建 Pull Request 对话框包含标题、描述和草稿模式选项" />
</Frame>

直接从你的工作空间创建 PR。

### 创建 PR

**从 Git 面板：**
1. 点击右侧边栏 Git 部分中的**打开 Pull Request**
2. 填写 PR 详情

**从命令栏：**
1. 按 `Cmd/Ctrl + K`
2. 选择**创建 Pull Request**

**PR 详情：**
   - **使用 AI 自动生成 PR 描述** - 让 AI 根据你的变更编写描述
   - **标题** - PR 标题（从任务名称自动填充）
   - **描述** - 关于变更的详细信息（可选）
   - **基础分支** - 要合并到的分支
   - **创建为草稿** - 标记为草稿 PR
4. 点击**创建 PR**

创建后，你的 PR 会出现在 GitHub 上，包含你的提交、描述和正在运行的 CI 检查。

<Frame>
<img style={{maxHeight: "400px"}} src="/images/workspaces-github-pr.png" alt="GitHub Pull Request 页面显示已创建的 PR 及其提交、检查和注释" />
</Frame>

### 草稿 PR

在以下情况下启用**草稿**模式：

- 工作仍在进行中
- 你希望在完成前获得早期反馈
- CI 检查应该运行但审查者不应合并

### 多仓库 PR

对于包含多个仓库的工作空间：

- 为每个仓库分别创建 PR
- 使用命令栏中的仓库操作
- 在描述中引用相关的 PR

<Tip>
尽早创建 PR 以获取 CI 反馈并让团队了解你的进展。
</Tip>

## 合并变更

将目标分支的最新变更拉取到你的工作分支中。

### 合并流程

**从 Git 面板：**
1. 点击**打开 Pull Request**旁边的下拉箭头
2. 选择**合并**

**从命令栏：**
1. 按 `Cmd/Ctrl + K` 并选择**合并**

确认后，目标分支的变更会合并到你的工作分支中。

### 合并前

工作空间会检查你是否落后于目标分支：

- **已是最新**：正常进行合并
- **落后于目标**：你将被提示先进行变基

<Warning>
始终确保 CI 检查通过且代码审查完成后再进行合并。
</Warning>

## 变基

保持你的分支与目标分支同步。

### 变基流程

**从 Git 面板：**
1. 点击目标分支下拉菜单（例如 **main**）
2. 从菜单中选择**变基**

**从命令栏：**
1. 按 `Cmd/Ctrl + K` 并选择**变基**

确认后，你的提交会在目标分支之上重新播放。

### 处理冲突

<Frame>
<img style={{maxHeight: "300px"}} src="/images/workspaces-conflict-dialog.png" alt="冲突解决对话框显示冲突文件列表及解决和中止选项" />
</Frame>

如果变基期间发生冲突：

1. 工作空间显示冲突解决对话框
2. 显示冲突文件列表
3. 在你的编辑器中解决冲突
4. 将文件标记为已解决
5. 继续或中止变基

### 何时变基

- 创建 Pull Request 之前
- 当目标分支有新提交时
- 合并前以确保干净的提交历史
- 当由于落后于目标分支而被提示时

## 更改目标分支

切换你要合并到的分支。

### 更改目标

**从 Git 面板：**
1. 点击 Git 部分中的目标分支下拉菜单（例如 **main**）
2. 从列表中选择新的目标分支

**从命令栏：**
1. 按 `Cmd/Ctrl + K` 并选择**更改目标分支**
2. 选择新的目标分支

工作空间会更新以显示新的领先/落后状态。

### 使用场景

- 从 `develop` 切换到 `main` 进行发布
- 目标设为功能分支而不是 main
- 更正错误设置的目标

## 推送变更

将你的提交推送到远程仓库。

### 推送何时可用

Push 命令在以下情况下出现：

- 你有未推送的提交
- 该分支有一个开放的 Pull Request

### 推送

**从 Git 面板：**
- 点击出现的 **Push** 按钮（当你有未推送的提交时显示）

**从命令栏：**
- 按 `Cmd/Ctrl + K` 并选择**推送**

提交会被推送到远程仓库。

<Info>
推送是上下文相关的 - 只在有变更需要推送且存在 PR 时才会出现。
</Info>

## 多仓库 Git 操作

对于包含多个仓库的工作空间，独立管理每个仓库。

### 每个仓库的操作

通过命令栏的**仓库操作**页面访问：

| 操作 | 描述 |
|------|------|
| 创建 PR | 为特定仓库创建 PR |
| 合并 | 仅合并特定仓库 |
| 变基 | 变基特定仓库 |
| 更改目标 | 更改特定仓库的目标 |

### 协调变更

跨仓库工作时：

1. 在每个仓库中进行相关变更
2. 创建相互引用的关联 PR
3. 按依赖关系正确的顺序合并
4. 合并后验证集成

## 冲突解决

当 Git 冲突发生时：

### 冲突对话框

工作空间显示冲突解决对话框，包含：

- 冲突文件列表
- 解决或中止的选项

### 解决步骤

1. 在编辑器中打开冲突文件
2. 手动解决冲突
3. 保存已解决的文件
4. 返回工作空间
5. 继续操作

### 中止

如果你无法解决冲突：

- 在冲突对话框中点击**中止**
- 操作被取消
- 你的分支恢复到之前的状态

<Warning>
未解决的冲突会阻止 Git 操作。始终在继续工作前解决或中止冲突。
</Warning>

## 最佳实践

### 分支管理

- 定期变基以与目标分支保持同步
- 尽早创建 PR 以获得可见性
- 使用描述性的分支名称
- 删除已合并的分支

### PR 工作流

1. 完成你的变更
2. 在变更面板中审查 Diff
3. 如果落后于目标则进行变基
4. 创建 PR（如果工作继续则标记为草稿）
5. 处理审查反馈
6. 批准后合并

### 多仓库协调

- 提前规划跨仓库变更
- 记录 PR 之间的依赖关系
- 按依赖顺序合并
- 充分测试集成

## 故障排除

<AccordionGroup>
<Accordion title="'You have uncommitted changes' 错误">
**含义：** 你有未提交的修改文件。

**解决方案：**
1. 让 Agent 完成当前工作（它可能即将提交）
2. 检查变更面板查看修改了什么
3. 使用终端提交变更：`git add . && git commit -m "WIP"`
4. 或者暂存它们：`git stash`
</Accordion>

<Accordion title="'Branch is behind target' 警告">
**含义：** 目标分支（例如 `main`）有你的工作分支没有的新提交。

**解决方案：** 变基你的分支以包含新变更：
1. 打开命令栏（`Cmd/Ctrl + K`）
2. 选择**变基**
3. 如果提示则解决冲突
</Accordion>

<Accordion title="变基期间的合并冲突">
**含义：** 你的变更和目标分支的变更修改了相同的代码行。

**解决方案：**
1. Vibe Kanban 显示列出受影响文件的冲突对话框
2. 在编辑器中打开每个冲突文件
3. 查找冲突标记（`<<<<<<<`、`=======`、`>>>>>>>`）
4. 选择要保留的版本（或组合它们）
5. 保存文件并将其标记为已解决
6. 继续变基

<Tip>
对于复杂的冲突，你可以让 Agent 帮助解决。发送一条描述冲突的新消息。
</Tip>
</Accordion>

<Accordion title="PR 创建失败">
**可能的原因：**
- 未通过 GitHub 认证
- 没有可以创建 PR 的变更
- 分支在远程不存在

**解决方案：**
1. 在设置 → 集成中检查 GitHub 集成
2. 确保你已提交变更
3. 尝试先通过终端推送分支
</Accordion>

<Accordion title="无法推送到远程">
**可能的原因：**
- 未配置远程仓库
- 认证问题
- 远程分支受保护

**解决方案：**
1. 验证远程仓库已配置：在终端中运行 `git remote -v`
2. 在设置中检查 GitHub 认证
3. 对于受保护的分支，创建 PR 而不是直接推送
</Accordion>
</AccordionGroup>
